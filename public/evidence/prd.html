2. 一句话定义与产品背景

OfficeFlow 把一条采购口语整理成可核对的入参，在人工确认后通过隔离浏览器登记固定后台表单，再独立查询实际记录，说明到底登记了什么。

原始痛点有两个。输入层要求用户照固定句式、品类白名单和编号填写，接近“把表单再说一遍”；执行层如果只以点击成功或页面回执为准，会无法区分后台已写入、提交未发生和结果未知。产品因此同时解决“少记格式”与“写入后能查证”。这是产品假设和工程目标，没有企业访谈、真实采购人员使用量或节省工时数据。

实际反馈推动了两个版本。用户输入“前台买一台打印机”，推动部门别名、中文数字、不同语序、自动编号和补全；随后输入“给行政买一打a4纸”，暴露品类封闭、规格数字被误当数量、单位缺失的问题。最新版本保留 A4 规格，整理为行政部 / A4纸 / 1 打，且把单位贯穿到批准、写入与证明。[E02、E03、E13]

可受益的假设用户是行政或运营登记人员，以及需要向下一位处理者交接结果的人。当前部署使用合成数据和独立体验租户，验证的是工作流工程可行性，不是实际采购履约。

角色/参与者能做什么权限边界

语言提案器提取有限字段、形成计划，标记实际来源不能批准、付款、访问用户指定外链或增加动作

核对/交接者阅读分层报告和核对包导出的包是观察快照，不是执行许可，也不是跨租户授权
维护者查看代码、测试、发布收据，维护适配器产品没有实现企业管理员、审批主管等独立角色体系

核心场景：一句话准备单条需求；最多 10 行准备多条未批准草稿；修订字段后重新确认；浏览器中断后只核对原编号；搜索与按部门/阶段筛选；向下一位处理者导出 1–10 条核对包。十条历史案例另设只读归档，不混入当前会话登记数。

6. 正常、失败、取消与恢复流程

正常单条链路：

原话 → 提取部门/名称规格/数量单位 → 缺项则保留原话并补全
    → 生成或保留 REQ 编号 → 有类型的规范入参
    → 服务端读目标版本并保存 draft → 预览完整计划
    → 人工批准当前版本（五分钟有效）→ 用户明确执行
    → 持久认领 executing → 短期能力 → 隔离浏览器固定表单
    → 提交载荷与批准一致 → 数据库条件写入
    → 新鲜 API 查询字段/哈希/业务键 → verified → 报告/核对包

“给行政买一打a4纸”不需用户自己编编号，输出行政部 / A4纸 / 数量 1 / 单位 打。A4纸500张装 的包装说明属于名称规格；若输入“买两包”，采购数量仍为 2 包。既不把 A4 中的 4 当数量，也不把 500 张包装算成采购 500 张。[E02、E13]

修订链路：展示旧字段与新字段差异 → 保留原需求编号 → revision 加一、重新读目标、清批准 → 回到 draft → 人工重新确认。执行中、未知效果、已登记和取消状态不能这样改。

失败与恢复示例：

  1. DOM（Document Object Model，文档对象模型）的字段标签、名称、数量或适配器不匹配，提交前停止；用户检查后刷新/修订并重新确认。
  2. 已批准两条，第一条登记改变租户目标版本，第二条不能沿用旧目标批准；先刷新目标重新预览再确认。
  3. 提交后回执丢失或查询失败，标记 unknown/需核对，保留可能或已发生效果；按原编号再次查询，不启动第二次浏览器提交。
  4. 取消先查结果，再通过并发控制停止新提交。事务写入前取消可阻止晚到写入；已经 applied 的登记保留，取消不是撤销或退款。

批量链路只是“逐行校验 → 顺序创建未批准草稿”。创建响应不确定时停止后续创建并查询已有草稿；每条之后仍需单独批准和执行。页面准备文本与已保存服务端草稿的生命周期不同。[E04、E09]

8. 状态机、业务规则与重试边界

运行状态 draft / approved / executing / unknown / verified / blocked / cancelled 与效果状态 none / unknown / applied 是两个轴。例如后台已 applied，但当前 API 查询失败，仍应显示“需核对”，不能擦除已写入事实。[E04、E10]

当前/目标允许条件与行为
无运行 → draft通过安全与字段校验，读目标，保存计划和哈希；不写登记表
draft/approved/blocked → draft无效果、无 result；匹配旧 revision/hash；同一编号；修订清批准
draft/approved/blocked → approved未产生效果；批准字段、适配器、当前目标一致；有效五分钟
approved → executing批准仍有效；目标未变；数据库尚无同键记录；CAS 认领成功
executing → verified独立查到相同载荷哈希和执行键的需求；保存 result/applied
executing → blocked浏览器证明提交不可能发生，安全检查停止；若仍可能有效则走 unknown
executing → unknown可能产生效果但无法确认，或认领/能力/提交中断；只查询恢复
unknown → verified原编号查到一致记录，不重写；未查到仍不能擅自判定可重试
活动前/活动中 → cancelled先查效果、再现场 CAS 停新提交；已 applied 保留，不撤销
已 verified 再执行/取消查询/记录事实，不能再次提交或声称撤销

CAS（Compare-and-Swap，比较并交换）用 epoch 比较现场版本，避免读到旧快照后覆盖别人刚写入的状态。执行认领租约超过 35 秒后只查询恢复；不是自动重新执行租约。短期能力期限不超过批准到期与签发后 30 秒的较早者。[E04、E06]

幂等分两层：页面按部门、物品、数量、单位的语义键复用无编号需求的生成编号；数据库以 (tenant_id, request_id) 唯一，并以稳定执行键约束效果。同编号不同载荷为 PAYLOAD_CONFLICT，不能覆盖。相同文字再次采购若确实是一笔新业务，应显式使用不同编号。跨页面、会话及真实外部系统的任意重试“恰好一次”不在承诺内。[E05、E08]

报告允许的下一步为 approve / execute / query-only / none。它是观察时的建议，不替代执行时服务端再次鉴权。页面“已完成”同时要求状态和新鲜 API 十项或九项检查匹配；仅有 verified 标签但报告未读或失效，仍属于需核对。[E09、E10]

存储有本地 SQLite 与云端 D1 两种适配，复用业务仓库接口；D1 是云托管 SQLite 数据库。单位添加到 JSON 记录，已有无单位载荷保持原规范字节，所以本次没有追加数据库迁移；历史结构已有迁移 1/2/3。[E08、E16]

计划哈希采用 SHA-256（Secure Hash Algorithm 256-bit，256 位安全散列算法），对固定字段顺序的规范 JSON 计算；提案来源不进入业务载荷，显式单位才附加 unit，旧无单位载荷保持不变。报告校验值对报告内容的规范 JSON 计算，是完整性检查，不能证明签发者身份或存储不可篡改。[E06、E10]

数据仅应是合成需求。用户仍可能误填私人信息，所以范围提示不是自动脱敏保证。公开报告排除会话、令牌、Cookie 和原始浏览器状态。当前没有查证到产品级数据删除入口、统一保留期、账号找回或跨设备迁移；会话到期不等于后台数据已删除，不能把归档当生产可执行数据迁移。[E01、E06、E08]

持久效果与查询观察分离已写入后查询失败必须诚实表达单个 success 布尔值无法表达 unknown；实现更复杂但便于安全恢复

12. Agent 职责、授权、模型、评测与回放

当前生产来源是 bounded-rule，界面明确显示“有界规则提案；模型未启用”。规则提取中文整数、部门别名、名称规格和计量片段，缺项由显式补全完成；不会让提案器猜部门、包装换算或执行授权。这里的 Agent 价值在于受控的“提案—批准—执行—证明—恢复”闭环，不以模型开启与否替代权限设计。[E03、E05、E17]

可选模型路径存在：本地 Ollama 使用已安装 qwen2.5-coder:7b-code；Workers AI 的源码使用 @cf/meta/llama-3.1-8b-instruct。两者都先运行规则基线，再对 JSON 做严格字段和原文对应校验；无效、超时或不可用回退规则并如实记 source。因此模型不能绕过当前规则不支持的输入，不能称“LLM 自动理解任何采购句子”。本地模型超时 15 秒、输出最多 512 token；云提案同为 15 秒、256 token。这里是源码参数，不是当前生产模型调用结果。[E17]

工具权力在服务端：批准绑定租户、运行、revision、载荷哈希、目标、适配器与到期；能力令牌短期有效；浏览器只访问受控来源和固定动作。文本中的支付、外链、权限或脚本不能增加工具权限。模型来源本身不进入业务哈希，但模型提出的业务字段仍完整绑定批准。

没有在线资料检索/RAG、开放网站规划、视觉/OCR 或自主多步骤工具探索。记录了运行事件、浏览器观测、持久结果、新鲜查询、发布版本；没有模型链式思考追踪和生产提示词质量平台。

历史模型评测必须分开说明：2026-10-04 使用 20 个冻结合成案例，规则和“模型＋严格验证/规则回退”均 20/20；其中只有三个正常输入实际来源为 Ollama，其余是规则层拒绝。该样本没有执行登记，notExecuted 指业务未执行，不表示没有模型请求。三个模型接受输出不足以证明 100% 模型准确率；也不能将当时样本倒推到最新单位/规格版本。另有 10 月 3 日一次原始模型返回，数量是字符串，HTTP 200 不等于满足严格 Plan。[E18]

历史回放是只读查看，不重放写入。unknown 恢复是查询原编号；核对包不是 replay 命令。独立代码审查的 Spec/Standards ALLOW 是工程审查结论，不是标定后的模型裁判准确率。[E03、E12]

17. 项目讲述：30 秒、90 秒与 5 分钟

以下“我主控、产品已上线”依据本人最新确认；具体“负责/实现/决定”须落到真实模块动作。证据数字可讲，不能将 AI 协作的全部操作讲成个人逐行手写。

30 秒稿

我主控的 OfficeFlow 已经上线，它把一句需求变成可核对的后台动作。用户描述需求，系统整理部门、物品、数量和单位，先预览并让人确认，再由隔离浏览器登记，最后独立查询结果。难点是自然语言歧义和提交后结果不明，所以采用有类型入参、版本批准、唯一键和查询恢复。10 月 8 日“给行政买一打A4纸”生产样本十项核对通过；当前运行使用有界规则和合成数据。

90 秒稿

我主控并已上线 OfficeFlow。产品背景是假设办公人员不想先学固定表单句式，但后台写入又必须可控。目标是把输入体验和执行可信度连起来：原话整理成字段，缺项让人补全，展示完整计划，确认后执行，结果再查证。

工作台使用 TypeScript，服务端在 Worker 上运行，D1 保存运行和需求，Playwright 只操作固定合成表单。本地有 Node、SQLite 和 Chromium 对应适配，便于复现故障。

我准备重点讲两个问题。第一，“一打A4纸”里 A4 是规格，1 打是采购计量，不能扫描所有数字，也不能猜包装换算。单位必须进入批准哈希、表单和 API 证明。第二，提交后断线不代表没写，所以先持久认领，再按原编号查询；已经可能生效的需求不自动重发，取消也不撤销已登记事实。

最新版本有 82 项单元集成和 63 项浏览器测试，预览与生产各一次实际云登记；生产十项核对通过，单样本浏览器耗时 5.280 秒。当前模型关闭，没有企业客户、开放语料准确率或 SLA 结论。我的具体负责模块和 AI 协作方式需要按真实经历补充。

5 分钟稿（八段讲清整个项目）

背景，约 30 秒。 我主控的 OfficeFlow 已上线。用户希望直接输入“前台买一台打印机”“给行政买一打A4纸”，而不是把编号、品类和固定格式都记住。另一方面，办公 Agent 如果只会点击提交，遇到断线就可能重复登记。项目把输入体验和效果核对一起考虑。当前验收在合成工作区，没有真实客户采购收益数据。

目标与边界，约 25 秒。 目标是明确需求可整理、每次写入有人确认、结果未知时安全恢复，而且能给下一位处理者看证据。范围只包含合成采购需求登记，不做付款、履约、任意网站或真实企业系统。部门目录有限，复杂语言可以澄清。

流程，约 35 秒。 用户原话先提取字段；缺项保留原话并补全；生成稳定编号，服务端保存 draft；预览字段及实际提案来源；批准当前版本；用户再明确执行。浏览器填写固定表单，后台事务写入，最后用新鲜查询核对字段和业务键。批量只准备草稿，后续仍逐条确认。

架构，约 35 秒。 前端是 TypeScript 和 Vite 的客户端页面，Pages Functions 转发到 Runtime Worker，D1 保存运行、目标版本、能力哈希和实际需求。受控 Browser Run 是写入口，查询走仓库。业务逻辑共用，本地用 Node、SQLite、Chromium。这样能够分别做本地故障验证和云端正常验收。

输入难点，约 40 秒。 旧版白名单拒绝纸张，扫描数字还会把 A4 或包装说明当数量。我会解释最新设计为什么把名称规格和计量分开：只提取“数量＋单位”或明确数量标签，A4纸500张装留在名称，采购两包就是 2 包，一打就是 1 打。只做整个名称的别名归一，打印机墨盒不能变成打印机。单位最终也进入哈希、批准、表单、持久化、证明和核对包。

执行难点，约 55 秒。 批准不是一个布尔值，而是当前计划版本、哈希、目标、适配器与五分钟期限。修订清旧批准。执行先用 CAS 认领，再发短期能力。写入时仍验证现场状态和唯一键，防晚到提交或取消竞态。浏览器看到回执与后台已写入要分开；API 暂时查不到不能证明没写。unknown 的恢复只能查原编号，不重新发起提交；applied 在取消后也不能擦掉。

取舍，约 30 秒。 生产关闭模型，有界规则可解释、成本可控，代价是覆盖有限。可选模型只提出字段并受严格验证，不能获取批准权。固定浏览器适配器适合演示旧网页，真实系统有可靠 API 时应重新评估写接口。旧无单位载荷保留原字节与 v1 证明，新单位进入 v2，避免升级破坏历史核对。

验证与反思，约 50 秒。 我会拿源码、测试、独审和生产分别说明。最新 82/63 测试包括自然语言、事务、取消、恢复和 UI；十条历史案例终点不同，但它们是本地归档。10 月 8 日预览生产各一次真实登记，原句在生产核对十项全真，独立回查也验证哈希。5.280 秒只是一例，不报云 p95 或业务收益。之后要补的是失败语料、生产监测、身份与生命周期；个人究竟承担了哪些模块必须据实回答。

18. 追问树与大白话复习

追问答题要点与证据大白话记法
1. 这为什么叫 Agent，模型没开还有价值吗？提案、审批、工具执行、观察、恢复是闭环；当前提案是有界规则，可选模型存在但不扩权。不能吹泛化智能。[E04、E17]会办事还要知道什么时候不能办
2. 为什么不直接让模型点网页？语言解释与执行权限分开；类型化字段、审批哈希、固定 DOM/POST。模型自由行动增加边界和复现成本。[E05、E07]先写清办事单，再按单办
3. 一打为什么不是 12？A4 的 4 怎么处理？数量和单位独立；保留 1 打，无包装换算假设；只读计量片段，规格/型号不当数量。[E02、E05]规格像商品标签，数量像购买份数
4. 自动编号会不会让真实第二笔采购消失？页面语义键避免同意图改语序重复；相同意图的新业务要不同编号。数据库同租户/编号不同内容拒绝，不是跨设备全局文本去重。[E05、E08]同一张单防重复，新一笔要新单号
5. 批准后还能改数量吗？只能安全阶段同编号 revise；匹配旧版本/hash，revision+1，清批准，展示 diff，再确认。执行中/unknown 禁止改。[E04]改了办事单，旧签字作废
6. 已经点过提交但断线怎么办？先持久认领；状态与 effect 分开；原编号新鲜查询；查不到也不能证明未写，不自动重发。[E04、E16]先查账，不能因为没收到回执再买一次
7. 取消和写入同时发生，谁赢？CAS 比现场 epoch，事务前核对 live run/目标/能力/批准。写前取消阻止效果；写后 applied 保留，取消不能撤销。[E04、E08、E12]以真正落账的时刻为界
8. 唯一键是不是证明恰好一次？唯一键限制这套数据库重复效果；网络和第三方系统仍可能不确定。须限定租户/编号/执行键与事务边界。[E08]本账本不重复，不等于全世界都不重复
9. 页面成功为什么还要 API？浏览器仅观察 DOM/POST/标记；数据库是持久效果；新鲜 API 对字段与哈希。查询失败仍保留 applied。[E10、E14]看到按钮变绿、后台写进账、再次查对账，是三件事
10. SHA-256 能证明报告谁签发、不可篡改吗？可验证内容一致性，非签名；有权修改内容的人也能重算。身份真实性需另设计可信签名/存储，当前未做。[E06、E10]校验码像校对尺，不是公章
11. 82＋63、20/20、十条历史分别是什么？82单元集成、63本地E2E；20旧模型回归含17规则拒绝，仅3来源Ollama；十条历史终点归档。生产增强一条，不能混算。[E03、E12、E13、E18]样本、试车、正式上路分别记账
12. 你具体做了什么、AI 做了什么？主控/上线已确认；进一步按模块说明自己作出的决策、审查/排障/验证与 AI 操作，给对应 PR/代码/收据；不能把主控等同全部手写主控责任和具体协作分工要一起讲
13. 为什么选择 Cloudflare？还能怎么做？Pages/Worker/D1/Browser Run 与已有合成发布边界匹配，资源可限制；Node服务器或数据库服务有不同运维代价。没有成本优越性对照试验。[E08、E11]选适合当前小闭环的工具，不宣称万能
14. 两条都批准，第一条写完为什么第二条停了？批准绑定 targetRevision；第一条改变后台目标版本；第二条刷新目标重预览/确认，批量草稿不能当连批连写。[E04、E09]环境变了，旧确认要重新看

复习时先能不看稿复述第 6 节链路，再讲清“原话/计划、批准/能力、运行/效果、观察/事实、测试/生产、项目/个人”六组区别。评审者追机制时指向自己的真实负责模块与证据，不用堆框架名字。
